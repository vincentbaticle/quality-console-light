Engage

Customer welcome

Recognises a returning customer from the company database, counts each visit, and shows the balance the partner bank holds for them. A closed or unknown customer is refused, a customer without a bank account is greeted without one.

  • Storefront API
  • MySQL customers
  • Redis visits
  • Bank Partner API

Try , , (no bank account) or (closed customer).

What this card teaches a tester
The form calls
GET /api/hello?username=: a SELECT in MySQL customers, an HTTP call to the Bank Partner, an INCR in Redis. Three neighbours, one click.
What is recorded
Not this page: a capture asks the real partner (mise run capture:examples), keeps its answers in capture/journal.json, then mise run capture:merge writes them as the examples Microcks replays (contracts/bank-partner-examples.yaml). See the Recorded examples tool.
Proved by
test_hello_redis.py (a Redis container), test_hello_customers_mysql.py (a MySQL container loaded from db/), test_hello_balance_microcks.py (a Microcks container replaying the recorded answers), and the browser test on the whole stack. Whether the real bank still keeps the contract Microcks replays: features/partner-contracts/, schemathesis generating requests from it.
Test it by hand
Say hello as ada twice: the visit number grows by one, the balance stays 1250.75 EUR. zoe: greeted, no balance (no bank account). dennis: refused, the API answers 404. Open Grafana: one trace per click, SELECT, the bank call, INCRBY.
Gherkin scenarios
features/customer-welcome/greeting.feature: a known customer greeted with the balance, every visit counted, no bank account, a closed customer refused; welcome-page.feature, this very form clicked by Playwright; load-baseline.feature, ten customers at once with k6. Run plays them on this stack.
How the container test works
A session fixture starts Redis (or MySQL, or Microcks) with testcontainers on a random port and yields its URL; the real app runs in process against it; the container is removed at the end. Locally its own containers, in CI the sidecars, same test code.
Test the test
Docker stopped: it skips and says why. Run twice: still green. Remove the INCR of a visit: test_second_visit_is_counted_in_redis turns red. The five checks: Testing with testcontainers.
Write yours
By hand: README, "Adding an API endpoint and its tests", four steps. With Claude Code: /new-api-test, which reads the same conventions.

Sell

Checkout

Places an order and follows it to the end. The API accepts it at once, then a worker reserves the stock, issues the invoice and captures the payment, one RabbitMQ event per step. Out of stock, the order is cancelled and the payment never attempted.

  • Storefront API
  • RabbitMQ
  • Order worker
  • MySQL orders and workflow state

Try (paid), (out of stock) or (closed customer).

    What this card teaches a tester
    The form calls
    POST /api/orders, answered 202 at once, then three RabbitMQ events (reserve_stock, issue_invoice, capture_payment) the worker handles one by one, writing MySQL. The page polls GET /api/orders/workflows/<id>.
    What is recorded
    The events the stack really publishes: mise run capture:events taps the broker's firehose while it places one order per story, mise run capture:events-merge writes contracts/order-workflow-recorded.yaml. Their contract: the AsyncAPI page of the API docs.
    Proved by
    test_orders_rabbitmq.py: a RabbitMQ and a MySQL container, the worker's handler run through drain, and the events compared with the recorded ones. The Gherkin feature checkout/place-order.feature on the running stack.
    Test it by hand
    ada buys Foundation: 202 at once, then three steps turn green, the order is paid. grace buys an Ultrabook: out of stock, cancelled, the payment step skipped. dennis: refused before any event. Then look: the queue in RabbitMQ, the new rows of the live tables in the console's Databases, the whole trace (API and worker) in Grafana.
    Gherkin scenarios
    features/checkout/place-order.feature: an order in stock paid step by step, an order out of stock cancelled before any payment, a closed customer refused; checkout-page.feature, this form filled by Playwright until the order reads paid. The journey and its gaps: Scenario design.
    How the container test works
    RabbitMQ and MySQL containers for the session; the test places the order through the real API, then runs the worker's own handle through drain instead of a running worker, so each step is checked in order; order_store restores the company data afterwards.
    Test the test
    Make the stock check always pass: the out-of-stock test turns red. Run twice: still green, the data was restored. Which tables the order really touches: retro-footprint. All the checks: Testing with testcontainers.
    Write yours
    A new neighbour: the four steps of "A new neighbour gets" in CLAUDE.md. With Claude Code: /new-api-test for the test, /new-gherkin-scenario for the scenario.

    Protect

    Account access

    Signs a customer in through a simulated Auth0 tenant. A new account has no password until its owner opens the link of the welcome email; a forgotten password gets a single-use link valid five days; ten wrong passwords block the account. Every email lands in the QA mailbox, one plus tag per account.

    • Identity API
    • MySQL users
    • QA mailbox

    Try (signs in), (blocked), (no password yet) or (asks for an authenticator code, like totp for ex.).

    No phone at hand? lin's app was enrolled with the secret OF2WC3DJOR4S2Y3PNZZW63DFFV2G65DQ: add it to an authenticator app, or the way a test does.

    Use a plus tag of the QA mailbox, for example .

    What this card teaches a tester
    The forms call
    /api/identity/login, /mfa/verify, /signup, /password-reset, /password: a simulated Auth0 tenant writing MySQL identity and sending its emails over SMTP to Mailpit, the QA mailbox.
    What is recorded
    Nothing to record: the emails are read live, as a test would read a real mailbox. Each test signs up its own plus tag (qa-mailbox+<tag>@mycompany.test), waits for its email, opens its link.
    Proved by
    test_identity_mailpit.py: a MySQL and a Mailpit container, the service in process. The Gherkin features of account-access/ on the stack, and their map in Scenario design.
    Test it by hand
    Sign in as ada: signed in. grace: blocked, told to check the email. zoe: no password yet. lin: asked for the code of an authenticator app; compute it, verify: signed in; verify the same code again after a new sign-in: refused, a code works once. Create an account with a new plus address, open the QA mailbox, follow the link, choose a password, sign in; open the same link again: refused, it works once.
    Gherkin scenarios
    features/account-access/: sign-in.feature (five scenarios, the second factor included) and account-emails.feature (five: welcome email, password set then sign-in, single-use link, reset link, ten wrong passwords that block), sign-in-page.feature (this sign-in form clicked by Playwright, with an account the scenario creates).
    How the container test works
    MySQL and Mailpit containers; the identity service runs in process, sends real SMTP to Mailpit; the test reads the mailbox through its API like a person reads an inbox (wait_for_email), extracts the link, follows it.
    Test the test
    Each test signs up its own plus address, so a rerun never meets a blocked account: run twice, still green. Let a link work twice: the single-use test turns red. All the checks: Testing with testcontainers.
    Sign in through a second factor
    A test keeps the TOTP secret beside the password and computes the code (tests/authenticator.py, pyotp): never a code about to expire, one retry with the next code if refused. Each test enrols its own account, so parallel jobs never spend each other's codes. See Account access.
    Write yours
    The mailbox helper is tests/mailbox.py. With Claude Code: /new-api-test, /new-gherkin-scenario.
