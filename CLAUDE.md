# quality-console, Claude Code project rules

Demo project of the QA team: a simulated company whose storefront offers three products (customer welcome, checkout, account access) on real services (nginx front, FastAPI API, a MySQL company database, Redis, RabbitMQ, a third-party Bank Partner, a simulated Auth0 tenant, a Mailpit QA mailbox), and its Quality Console (catalog, databases, test results, QA tools), tested with testcontainers, the partner replayed by Microcks from captured examples, every API call traced with OpenTelemetry into a local Grafana LGTM stack when run by hand. Keep it small enough to be explained in a talk; every new test must stay readable by someone who never saw testcontainers.

## Layout

- `src/hello_api/greeting.py`: pure rules. `src/hello_api/main.py`: routes, built by `create_app(redis_url, partner_url, database)`.
- `src/company_db/`: `DatabaseSettings`, `settings_from_environment()` (the `DB_*` variables) and `connect()`, shared by every service reading the company database.
- `src/hello_api/customers.py`: the `customers` read (active customers only).
- `src/quality_console/`: the Quality Console (`main.py` assembles the routers from a `ConsoleSettings` (`settings.py`), `databases.py` + `database_pages.py` the database browser, `results.py` the test results pages, `catalog_pages.py` the catalog, `tools/` one router per tool (`apis`, `gherkin`, `skills`, `bucket`, registry in `tools/__init__.py`), pure readers `gherkin_files.py`, `skills_files.py`, `asyncapi.py`, SVG charts `charts.py`, `templates/` renders; the look lives in the tokens of `templates/base.html`, light and dark), run by the `console` service on port 8081 as `console_reader`, a `SELECT`-only account. Any identifier from a request is checked against what MySQL lists before reaching a statement; values are bound.
- `src/hello_api/orders.py` + `src/order_workflow/`: the event-driven order workflow. `steps.py` (pure: step order, invoice number), `broker.py` (RabbitMQ queue `order-workflow`, thin events `{workflow_id, type}`), `store.py` (writes in `mycompany` and `orchestrator`), `worker.py` (`handle` runs one step and publishes the next; `python -m order_workflow.worker`, service `worker`). Tests run the worker's `handle` through `drain` instead of a running worker, and use the `order_store` fixture, which restores the company data after the test.
- `src/hello_api/bank_partner.py`: client of the Bank Partner (`404` means no account, anything else but `200` is a `502`). Money travels in integer cents and is formatted by `format_amount`, never through a float.
- `frontend/`: `index.html` (a product list, then one section per product shown alone by its hash `#welcome`, `#checkout`, `#account`, with a way back), `app.js` (forms that call an API wait at least one second behind a spinner, nothing else does), `nginx.conf` (proxies `/api/identity/` to the `identity` alias, resolved at request time, and `/api/` to `api`).
- `src/identity/`: the simulated Auth0 tenant. `rules.py` (pure: lowercase emails, plus tags, password policy and hash, ticket TTL, link extraction), `totp.py` (pure: the second factor's codes, RFC 6238), `mfa.py` (its routes), `models.py` (shared bodies), `store.py` (database `identity`), `emails.py` (contents and SMTP), `tenant.py` (behaviour, refusals as `TenantError`), `main.py` (routes). Service `identity`, emails to Mailpit (`mailpit`, UI 8025).
- `catalog/catalog.yaml` + `src/catalog/`: the software catalog as code, `sql.py` renders `db/05-catalog.sql` (`mise run catalog:sql`), `reader.py` reads it back for the console. Never edit `db/05-catalog.sql` by hand.
- `src/gherkin_runner/`: runs `pytest tests/acceptance` narrowed with `--only-feature` / `--only-scenario`, uploads the run (service `runner`).
- `features/<product>/*.feature` + `tests/acceptance/test_<product>.py`: Gherkin scenarios (pytest-bdd), marker `acceptance`, against the running stack only; shared steps and the filter in `tests/acceptance/conftest.py`. Every scenario carries a `Goal:` description line (checked by `test_every_scenario_of_the_repository_says_its_goal`). A `@tool-<name>` tag above `Feature:` names what drives it (pytest, playwright, schemathesis, k6), shown as a badge by the console and kept out of the pytest markers by `pytest_bdd_apply_tag`. `@recorded` features (`*-page.feature`) follow the template of `quality_console/scenario_template.py` (one Given per actor `"<actor>", a <account type> who <rights>`, a data Given, a Then; checked by `tests/unit/test_scenario_template.py`) and click the storefront with Playwright through the `page` fixture of `tests/acceptance/conftest.py` (the runner image carries Chromium); `/record-scenario` writes them from a Codegen recording cleaned by `quality_console/recording_scrub.py` (`scripts/scrub_recording.py`). `customer-welcome/load-baseline.feature` runs k6 (`perf/`, pinned in `.mise.toml`, copied into the runner image). `partner-contracts/` runs schemathesis (dev dependency) inside its steps against the `partner` service (`PARTNER_URL`), from `contracts/bank-partner-openapi.yaml` (mounted in the runner).
- `contracts/`: every API contract. Bank Partner (Microcks primary + examples), order workflow events (AsyncAPI), and the OpenAPI of our own services, written by `mise run contracts:export`, never by hand.
- `.claude/skills/`: the project skills Claude Code loads in this repository.
- `designs/*.yaml`: scenario designs (nodes, edges, the path of each scenario), drawn by the console (`quality_console/designs.py`); every path must name a scenario of `features/`.
- `buckets/`: files of the demo team buckets, loaded into the storage emulator (`-data`); checked by `features/bucket-checks/`.
- `audio-assets/` (folder committed, files not) + `quality_console/audio_assets.py` (rules, synthesis with `numpy`, writing with `soundfile`) + `tools/audio_assets.py` (page `/utility/audio-assets`, JSON `POST .../generate`, `GET`/`DELETE .../files/<name>` for listed files only): the audio asset generator, the console's only write to the repository, mounted read-write as `AUDIO_ASSETS_DIR`.
- `capture/` (not committed) + `scripts/capture_*.py` + `scripts/merge_captured_*.py`: recordings. Bank Partner answers into `contracts/bank-partner-examples.yaml`, order workflow events (RabbitMQ firehose) into `contracts/order-workflow-recorded.yaml`; shown by the Recordings tool.
- Console tools added later: `tools/designs.py`, `tools/recordings.py`, and the DevX tools under `/devx`: `tools/footprint.py` (pure rules in `quality_console/footprint.py`: the tests to run, pages of a front, API calls and SQL of their own; the real runs in `footprint_lab.py`, two batches of five 20 seconds apart: `performance_schema` counters, colleague queries, real calls through `API_URL`, `FRONT_URL` and `CONSOLE_URL`, the trace searched in Tempo through `TEMPO_URL`, one thread per experiment polled as JSON). The registry's `section` puts a tool in the Static Cockpit QA (`cockpit`), DevX (`devx`) or Utility tools (`utility`, page `/utility`), its `kind` labels the tool card (`live`, `static`, `mixed`, `mock`); a tool whose `path` is `/tools/docs?page=<slug>` is a guide, a page of `docs/` shown as a card (`sonar-decom`, the MCP server). `quality_console/table_kinds.py` tags each table, bucket and Gherkin product `live` (changed by using the stack) or `static`. DevX also holds the tips (`/devx/tips`, `templates/_tips.html`, one tab per topic, the front design demos in plain JS and SVG, the static image in `quality_console/static/`). `tools/docs.py` + `docs_files.py` show every page of `docs/` (mounted as `DOCS_DIR`); a tool's `doc` field names its page and `base.html` links to it, top right; a new tool gets its page in `docs/`. Every console page has a blue `.info` box saying what its buttons do; `base.html` shows a loader only for a link or form carrying `data-loading`, kept for actions that call an API or a database, never for plain navigation.
- `perf/*.js` + `scripts/perf_and_upload.sh` (`mise run test:perf`): k6 load tests against the running stack; `handleSummary` writes `summary.json` (the flat shape `test_results/k6.py` reads) and a `junit.xml` with one case per threshold carrying the metadata properties.
- `src/quality_mcp/` + `.mcp.json`: the MCP server over the local stack (`tools.py` plain methods, `server.py` FastMCP over stdio, `mcp` in the dev group); the runner is published on 8082 for it. See `docs/mcp.md`.
- `vault/` + `src/company_secrets/`: Vault in dev mode (`vault`, `vault-init`, `vault-agent` in `docker-compose.yml`). The agent (AppRole) renders short-lived MySQL and RabbitMQ users (2 min, renewed up to 6) and the Bank Partner's long-lived key into `/vault/secrets/<service>/*.env`; services read them at each connection (`DB_CREDENTIALS_FILE`, `RABBITMQ_CREDENTIALS_FILE`, `BANK_PARTNER_API_KEY_FILE`) and fall back to the environment without them (integration tests). Tests read the bank key from Vault with `hvac` and `tests-token`. The console page `/devx/vault` (`vault_view.py`) reads leases and metadata with `console-token`, never a value. See `docs/vault.md`.
- `src/quality_console/snapshot.py` (pure: page keys, which pages are left out, file names, link rewriting, the banner) + `scripts/freeze_console.py` (`mise run demo:freeze`, the crawl, GET only, into `site/`, not committed) + `.github/workflows/pages.yml`: the static demo on GitHub Pages, rebuilt on each push to `main`. `.devcontainer/` runs the live stack in a Codespace. A new console route that writes must not answer GET, or the crawl would trigger it.
- `mocks/router.mjs` (service `mocks`, port 4010): Stoplight Prism on every `contracts/<name>-openapi.yaml`, served under `/<name>/`; `/` lists them. Linked from the API docs page (`MOCKS_URL`). Microcks stays for the Bank Partner's captured examples: Prism cannot pick an example by request. Tested by `tests/integration/test_contract_mocks_prism.py` (no CI sidecar: it needs `contracts/` mounted, so it skips in sidecar mode).
- `announcements/` + `quality_console/announcements.py` + `tools/announcements.py`: the release announcements `/announce-release` (team skill) drafts, one file `<YYYY-MM-DD>-<system>-<version>.md` each, shown in the cockpit with the `Versions:` footer the next run starts from. No em dash in them.
- `partner/`: the fake Bank Partner, reading `bank_accounts` in the same database, only ever run by hand to be captured. Tests never call it.
- `db/`: `01-schema.sql` (30 tables with foreign keys), `02-seed.sql` (10 hand-written rows each, the ones tests name), `02b-volume.sql` (generated rows, up to 113 per table, `ROW_COUNTS` of `tests/database.py`), `03-console-reader.sql` (the console's read-only account, plus the `performance_schema` table counters for the footprint), `04-orchestrator.sql` (the workflow state store), `05-catalog.sql` (generated) and `06-identity.sql` (identity users; the console reads the views `accounts` and `password_links` only), loaded by `docker-compose.yml` (init directory) and by `tests/database.py` (through a client, so a CI sidecar works too). Change a row count in `02b-volume.sql` and `ROW_COUNTS` together, never above 113: `test_company_database_is_loaded_in_full` checks both.
- `docs/demos/`: the three demo scripts (testcontainers, observability, Quality Console). `docs/`: one page per product or tool (`test-results.md`, `order-workflow.md`, `account-access.md`, `catalog-and-metadata.md`, `gherkin.md`, `api-contracts.md`, `retro-footprint.md`, `databases.md`, `bucket-browser.md`, `tips.md`, `audio-assets.md`, `mcp.md`, `recorded-scenarios.md`, `vault.md`) and the general guides `testing-with-testcontainers.md` and `sonar-decom.md` (`GUIDES` of `docs_files.py`).
- `src/test_results/`: the results bucket contract (layout, models, JUnit and k6 parsing, uploader, indexer, reader). The run folder name (`run_folder_name`) is UTC and zero-padded on purpose: keep it. Readers only read paths `is_report_path` accepts.
- `scripts/test_and_upload.sh`: what the mise test tasks run, pytest then the upload, the tests' exit code kept. `scripts/seed_results.py`: the made-up history, deterministic, written through `upload_run` so it has the real shape.
- Telemetry: no OpenTelemetry code in `src/` or `partner/`. Every service starts with `opentelemetry-instrument`; the packages are the `telemetry` optional group of `pyproject.toml` and the `pip install` of `partner/Dockerfile`; the `OTEL_*` settings live in `docker-compose.yml`. Tests run with `OTEL_SDK_DISABLED=true`.
- `contracts/bank-partner-*.yaml`: the partner's contract (primary Microcks artifact) and examples (secondary). Captured examples come from `mise run capture:examples` then `mise run capture:merge`; hand-written ones (errors) are never touched by the merge.
- `tests/story.py`: the captured usernames and the balances the bank answered for them. A recapture that changes a value updates it in the same commit.
- `tests/microcks.py`: Microcks constants and artifact upload (Bank Partner).
- `tests/mailbox.py`: reading the QA mailbox like a test does (`wait_for_email`, the link, its ticket).
- `tests/authenticator.py`: signing in through the second factor like a test does (`fresh_code`, `codes`: a fresh code, then the next one), with `pyotp`.
- `tests/metadata.py`: `metadata_test(...)`, the test runner's metadata fields as a pytest marker.
- `tests/neighbours.py`: image names, ports, `require_docker()`, `uses_external_services()`.
- `tests/database.py`: waits for a MySQL login, then recreates `mycompany` from `db/`.
- `tests/integration/conftest.py`: every container fixture. Tests never start a container themselves.
- `gitlab-ci/`: `mocks.yml` holds stand-ins for the shared building blocks (pre-commit, SonarQube); no job may call an external service.

## Conventions for a new endpoint

- Follow the worked example of `README.md` ("Adding an API endpoint and its tests"): a pydantic response model, a route inside `create_app`, `Username` for a `username` parameter, `visits_key` for any Redis key of a visitor.
- Pure rules go in `src/hello_api/greeting.py` (or a sibling pure module), with a unit test. Routes hold no rule of their own.
- Every new endpoint gets an API test (`api` fixture, or `console` for the Quality Console): happy path, one refusal, and what lands in Redis (`redis_client`). A browser test only when the front changes.
- When `main.py` grows past a handful of routes, move routes to an `APIRouter` module per feature in the same change.

## Conventions for a new test

- Three markers: `unit` (pure logic, no I/O), `integration` (a real neighbour), `acceptance` (a Gherkin scenario on the running stack). Set it in `pytestmark` at module level.
- File name suffix names the neighbour: `test_<feature>_redis.py`, `test_<feature>_mysql.py`, `test_<feature>_microcks.py`, `test_<feature>_gcs.py`, `test_<feature>_rabbitmq.py`, `test_<feature>_mailpit.py`, `test_<feature>_browser.py`.
- Every test module declares `metadata_test(system, product, business_capability, component, group, testing_scope, tags)` in its `pytestmark` (a test or class may override it with the decorator). Values must be entries of `catalog/catalog.yaml`: `tests/unit/test_metadata_catalog.py` checks it. `tests/conftest.py` writes them as JUnit properties, the console filters on them.
- A test that writes shared data uses its own: a new plus tag of the QA mailbox (`plus_address`), never a seeded account it could block.
- Never hand-edit a captured example: change the partner or the story, capture, merge, review the diff. Only error examples are written by hand.
- A new partner API is not a new neighbour: it is a new contract and examples pair loaded into the same Microcks.
- No mock across a boundary, no `unittest.mock` in `tests/integration/`.
- A new neighbour gets:
    1. its image and internal port as documented constants in `tests/neighbours.py`;
    2. a session fixture in `tests/integration/conftest.py` that calls `require_docker()` locally, attaches to a sidecar when `uses_external_services()` is true, and yields connection data built from `get_container_host_ip()` and `get_exposed_port()`, never a hardcoded host port;
    3. the matching `testcontainers[<extra>]` in the `dev` dependency group, then `pdm install` (which updates `pdm.lock`);
    4. a sidecar plus its host variable in the `integration-tests` job of `gitlab-ci/tests_stage.yml`.
- Each test starts from a clean state (see `redis_client`, which flushes before each test). The database is read-only for the API, loaded once per session; a test that writes to it must restore what it changed.
- Browser tests use `get_by_role` / `get_by_label` and `expect(...)`, never sleeps.

## Before calling a change done

1. `mise run hooks:run` green.
2. `mise run test` green, then run it a second time: still green with no manual cleanup. A product change also runs `mise run test:acceptance` against `mise run up`.
3. With Docker stopped, integration tests skip with a reason instead of failing.
4. `README.md`, the matching page of `docs/` and the demo scripts of `docs/demos/` updated when a level, a neighbour, a page, a tool or a command changes.
5. `mise run catalog:sql` and `mise run contracts:export` rerun when the catalog or a route changed (unit tests fail otherwise).
6. New files are staged before `mise run hooks:run`: prek only sees tracked files.

## Repo-specific values

- Whole-tree hook command: `mise run hooks:run`.
- Main branch: `main`.
- No MR template, no version in `pyproject.toml`: this is a demo. Releases are git tags only, picked by cocogitto from the commit types since the last tag (`mise run release:check`, then `mise run release`). A `chore`, `docs`, `refactor` or `test` commit alone gives no tag: type a release-worthy change `fix` or `feat`.
